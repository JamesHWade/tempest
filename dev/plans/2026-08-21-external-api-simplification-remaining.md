## PR C — reset expert and product schemas

### Implemented but not yet frozen

- `tempest_expert()` accepts only `name`, `title`, `description`,
  `instructions`, `focus_areas`, and `initial_questions`.
- Expert identity and version are derived from canonical authored content.
- Generic capability, skill, policy, selection, state, metadata, and duplicate
  work-item fields have been removed from the profile and runtime bindings.
- Retirement is session-roster state rather than mutable expert-profile state.
- The expert record is schema 2; STORM state is schema 5; STORM bundle is
  schema 8; Co-STORM snapshot and bundle are schema 10.
- Co-STORM persistence has an explicit `retired_expert_ids` record and restores
  roster retirement separately from immutable expert profiles.
- Generated experts use the same canonical constructor as supplied experts.
- Initial focused expert and STORM-state tests have been rewritten, but the
  wider fixture migration is incomplete.

### Resolve the remaining expert-provenance seam

Expert identity must remain a pure function of canonical profile content. It
must not encode whether a profile was supplied by the caller or generated by a
personas stage.

- [x] Remove the obsolete `expert.generated-` prefix test from
  `tempest_stage_records_validate_generated_experts()`.
- [x] Treat a succeeded personas StageRecord as the generation-provenance
  record. When present, require its content digest to bind an exact canonical
  prefix or singleton of the durable expert roster.
- [x] Do not infer generation origin from an expert profile when no personas
  StageRecord exists; the same authored profile can legitimately be supplied
  explicitly.
- [x] Update the STORM authority test to prove both sides of this contract:
  absence of a personas record is valid for an explicit roster, while a
  present personas record must match the exact expert content
  (`tests/testthat/test-storm-state.R`).
- [x] Confirm generated product paths always create and persist the personas
  StageRecord, and that resume retains it. `tests/testthat/test-storm.R`
  proves a supplied roster records zero personas records, a generated roster
  records exactly one succeeded personas record whose digest equals
  `tempest_stage_state_output_digest("personas", experts)`, and that resume
  returns byte-identical stage-record data.

StageRecord schema 3 should remain unchanged if its output-reference payload
shape is still `kind`, `ids`, and `content_digest`. A changed digest value from
the new expert record does not itself require a StageRecord schema bump.

## Native stack operating procedure

- Every layer keeps a narrow commit and a base equal to the branch immediately
  below it.
- Create each new pull request as a draft, then append it with
  `gh stack link <stack-number> <pr-number>`.
- Verify the pull request REST `stack` object, exact head SHA, base branch,
  position, stack size, and CI after every link or push.
- Make fixes on the owning lower branch and use the stack tooling to cascade
  them upward; do not duplicate the fix in later layers.
- Mark a layer ready only after its exact-head local gates and draft CI are
  green. Treat the ready-triggered review as a separate required check.
- Do not merge individual layers with the legacy synchronous PR merge API.
- When every intended layer is ready and green and the user authorizes the
  merge, use GitHub's native stack merge on the highest approved layer. This
  must be an all-or-nothing merge of the contiguous stack prefix.
