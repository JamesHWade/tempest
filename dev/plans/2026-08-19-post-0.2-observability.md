# Post-0.2 privacy-safe observability plan

Tracking issue: `bavj` (parent: `0wh9`)

Status: implemented and verified

## Goal

Add a small, experimental, off-by-default OpenTelemetry trace projection for
live STORM and Co-STORM operations. Reuse Tempest's existing progress-event
contract, preserve the package's exact product authority boundaries, and make
local OTLP/HTTP export possible without making Tempest own a collector or a
backend.

This is post-0.2 product work, not T11. T10 completed the 0.2 migration and
release. Observability is a separate, optional host integration.

## Decision

Use the maintained R `otel` instrumentation API behind one internal Tempest
adapter. Do not add a Logfire dependency or implement OTLP ourselves.

The supported topology is:

```text
Tempest operation and progress events
  -> optional internal otel instrumentation
  -> host-configured R OpenTelemetry provider
  -> OTLP/HTTP
  -> local OpenTelemetry Collector
  -> operator-selected backend
```

Logfire may be one external destination selected by an operator. It is not the
Tempest API, collector, default, or local-development runtime. Its self-hosted
product requires substantially more infrastructure than this package should
own. A local OpenTelemetry Collector is the bounded open integration point.

The R OpenTelemetry implementation is maintained and usable, but remains
pre-1.0 and is classified as Development rather than an official stable
OpenTelemetry language SDK. Therefore the Tempest integration remains
experimental, internal, and optional.

Relevant upstream references:

- [OpenTelemetry language support](https://opentelemetry.io/docs/languages/)
- [R OpenTelemetry status and API](https://otel.r-lib.org/)
- [`otel` 0.2.0](https://github.com/r-lib/otel/releases/tag/v0.2.0)
- [`otelsdk` 0.2.4](https://github.com/r-lib/otelsdk/releases/tag/v0.2.4)
- [OpenTelemetry Collector quickstart](https://opentelemetry.io/docs/collector/quick-start/)
- [Mirai OpenTelemetry propagation](https://mirai.r-lib.org/articles/v05-opentelemetry.html)
- [Shiny OpenTelemetry guidance](https://shiny.posit.co/r/reference/shiny/1.12.0/upgrade.html)

## Non-goals

- Do not add a second event ledger, telemetry database, trace persistence
  format, snapshot field, bundle file, schema version, or migration reader.
- Do not make telemetry authoritative for product state, report publication,
  Deputy execution, dsprrr programs, Graft acceptance, or trajectory review.
- Do not add a Logfire package, token, endpoint, SDK, hosted-service account,
  self-hosted deployment, or vendor-specific attribute contract.
- Do not implement an OTLP client, exporter, queue, retry policy, sampler,
  collector, backend, flush manager, or shutdown hook in Tempest.
- Do not emit metrics, logs, profiles, baggage, or custom propagation in the
  first implementation.
- Do not export prompts, model responses, queries, claims, evidence, source
  bodies, URLs, file paths, headers, tool inputs or outputs, credentials, or
  arbitrary R objects.
- Do not call `otel::as_attributes()` on general objects or record exception
  objects, messages, calls, or stack traces.
- Do not duplicate spans already emitted by Shiny, Mirai, ellmer, promises, or
  httr2.
- Do not keep a span handle open for the lifetime of a mutable Co-STORM
  session. The product has no explicit close boundary that could guarantee the
  span ends. Trace bounded turn, warmup, and report operations instead.
- Do not attribute token usage or cost to a Tempest run. The available ellmer
  token counter is process-global and cannot safely identify concurrent runs.
- Do not add a stable public telemetry API until the R OpenTelemetry stack and
  the Tempest projection have demonstrated a stable contract.
- Do not redesign the bundled Shiny UI, change its 13-member store or
  10-member public server handle, or add a telemetry dashboard in this stack.

## Frozen product boundaries

The work must preserve:

- exactly 63 exports and exactly two registered S3 methods;
- the current public signatures of `tempest_run()`, `tempest_session()`, and
  the progress-event functions;
- the existing Workspace 5, Co-STORM 9, STORM bundle 7/state 4, ProgramSet 2,
  Manifest 3, StageRecord digest 3, and promotion 1 schemas;
- exact report, publication, persistence, trajectory, and promotion authority;
- existing progress callback ordering, values, and failure behavior;
- deterministic results and serialized product bytes with telemetry enabled
  or disabled; and
- no network, API key, provider, collector, or external service in tests.

Telemetry is an ephemeral, lossy operational projection. A missing, partial,
duplicated, or failed trace can never change or invalidate a Tempest product.

## Configuration boundary

Add `otel (>= 0.2.0)` to `Suggests`, not `Imports`. Do not add `otelsdk` as a
runtime dependency. A developer may use `otelsdk` in a separate local smoke
environment, but the package test suite must exercise a mockable Tempest-owned
seam and remain independent of a compiled SDK and external service.

Instrumentation is active only when all five conditions hold:

1. `getOption("tempest.otel.enabled", FALSE)` is exactly `TRUE`;
2. `otel` is installed; and
3. `OTEL_R_EMIT_SCOPES` is exactly the single value
   `io.github.jameshwade.tempest`; and
4. `OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT` is unset or exactly
   `false` after trim and case normalization; and
5. the selected OpenTelemetry tracer is enabled.

The transportable worker opt-in is only the conjunction of conditions 1, 3,
and 4. A worker sets that boolean as a local option, then independently checks
for `otel` and its own tracer before starting a span. Host-process tracer state
is never treated as worker-provider authority.

Otherwise the adapter is a no-op. Tempest never creates or replaces the
provider and never sets `OTEL_*` variables. The host owns exporter, endpoint,
headers, TLS, resource attributes, sampling, batching, and shutdown. Tokens
belong in the collector or host environment, never a `TempestConfig`, session,
snapshot, bundle, log, or example committed to the repository.

The bundled app must not silently enable telemetry or mutate Shiny's global
OpenTelemetry options.

The only supported profile in this stack must set
`OTEL_R_EMIT_SCOPES=io.github.jameshwade.tempest` before R starts. Without a
scope restriction, an enabled provider can independently collect telemetry
from ellmer, httr2, Mirai, Shiny, and other instrumented packages. Those spans
are outside Tempest's projection and may include full URLs, query strings,
tool errors, identifiers, or other fields prohibited here. A broader or
wildcard scope makes the Tempest adapter a no-op and is unsupported until each
additional package scope receives a separate privacy audit.
Setting `OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT=true` is an
explicit host decision to export model conversation content and disables the
Tempest adapter in this stack.

## Trace contract

### Instrumentation scope

Use one fixed instrumentation scope: `io.github.jameshwade.tempest`.

The initial fixed span names are:

- `tempest.storm.run`
- `tempest.costorm.completion`
- `tempest.costorm.turn.commit`
- `tempest.costorm.warmup`
- `tempest.costorm.report`
- `tempest.stage.execute`
- `tempest.retrieval.search`
- `tempest.retrieval.fetch`

The matching fixed operation values are `storm.run`, `costorm.completion`,
`costorm.turn.commit`, `costorm.warmup`, `costorm.report`, `stage.execute`,
`retrieval.search`, and `retrieval.fetch`. Executor stage attributes must be
members of `tempest_program_stages()`.

The progress-stage allowlist is exactly `dialogue`, `evidence`, `mindmap`,
`outline`, `persistence`, `perspectives`, `polish`, `report`, `research`,
`session`, `suggestions`, `verification`, `warmup`, and `write`. The
progress-step allowlist is exactly `created`, `delegate_to_expert`,
`expert_fanout`, `fact_extraction`, `generate`, `moderator_response`,
`question_generation`, `report_md`, `turn`, `update`, `user_turn`,
`perspectives_artifacts`, `research_artifacts`, `outline_artifacts`,
`write_artifacts`, and `polish_artifacts`.

Names never contain user data, provider names, topics, queries, stages, model
text, or identifiers. The required Tempest-only scope suppresses automatic
Mirai, ellmer, promises, Shiny, and httr2 spans. Distributed parentage and
dependency spans are not part of the initial supported profile.

### Progress-event projection

`tempest_emit_progress()` is the single live event observation seam. It records
one fixed `tempest.progress` span event on the current Tempest operation span,
then preserves the existing host callback behavior exactly.

Starting an operation snapshots the enabled gate and tracer into one
operation-local context containing a package-private sentinel, the span handle,
a generation token, and an `ended` flag. Annotation and cleanup receive that
context directly and never re-read global options or look up a different run.
Synchronous wrappers bind it under the exact local name
`.tempest_otel_context`; an internal lookup scans the nearest live call frame
and accepts only the package sentinel. Later async call sites may pass their
captured context explicitly. The event seam calls that exact handle's
`add_event()` method and never discovers or annotates the ambient OTel span. A
missing or ended context is a no-op. The context is ephemeral process state and
is never serialized. A session-construction or restore event emitted outside
an owned operation has no context and produces no telemetry.

The adapter may project only these validated fields:

- `workflow`, `event_type`, and `status`, because they are closed enums; and
- `stage` or `step` only after exact membership in a package-owned closed
  allowlist. Unknown values are omitted, not copied or normalized.

It never projects `message`, `payload`, `run_id`, `event_id`,
`parent_event_id`, `correlation_id`, or `timestamp`. Those fields are useful to
host progress consumers but are not all credential-audited, low-cardinality,
or authoritative enough for the first trace contract. Replayed/restored events
do not create telemetry.

The complete fixed attribute-key fixture is:

- `tempest.workflow`
- `tempest.operation`
- `tempest.event_type`
- `tempest.stage`
- `tempest.step`
- `tempest.status`
- `tempest.cache_hit`
- `tempest.result_count`
- `tempest.fallback_taken`
- `tempest.cancelled`
- `tempest.error_class`

No attribute accepts an arbitrary string. Stages and operations use closed
package constants. Error classes use a closed set and fall back to
`tempest_operation_error`; error messages and condition objects are excluded.
Counts are finite non-negative integers. OTel span status is exactly `unset`,
`ok`, or `error`: a succeeded terminal operation maps to `ok`, a failed
operation maps to `error`, and pending/running/partial/skipped/cancelled states
remain `unset`. A partial Co-STORM result carries only the closed
`tempest.status = "partial"` attribute. Cancellation is represented only by
the safe `tempest.cancelled = TRUE` attribute. No thrown condition is recorded.

The exact terminal projection is:

| Product outcome | Tempest attributes | OTel status |
|---|---|---|
| success | `tempest.status = "succeeded"` | `ok` |
| fallback success | succeeded plus `tempest.fallback_taken = TRUE` | `ok` |
| failure | `tempest.status = "failed"` plus safe error class | `error` |
| cancellation | `tempest.status = "cancelled"`, `tempest.cancelled = TRUE` | `unset` |
| partial | `tempest.status = "partial"` | `unset` |

The error-class allowlist is the union of
`tempest_stage_failure_classes()` and exactly `tempest_run_cancelled`,
`tempest_run_error`, `tempest_progress_callback_error`,
`tempest_async_cancelled`, `tempest_async_error`, and
`tempest_operation_error`. Every other condition maps to
`tempest_operation_error` without inspecting its message, call, or fields.

### Async and cancellation semantics

- Start `tempest.storm.run` inside the process that actually executes
  `tempest_run()`. Do not wrap the bundled app's direct Mirai dispatch with a
  duplicate Tempest span. The Tempest-only profile intentionally produces an
  independent root in the worker. Do not serialize trace context manually.
- Use `otel::start_span()` and activate the owned span only around the immediate
  synchronous operation or async dispatch, with automatic end-on-exit disabled.
  Do not use helpers that automatically record thrown condition objects.
- For a promise-returning operation, retain the owned span handle only in that
  operation's closure, update it through safe explicit success/failure handlers,
  and end it once from `promises::finally()`. Tempest does not install a custom
  promise domain. Async call sites that have the explicit operation context may
  annotate it directly; ambient promise callbacks never discover a span.
- The `ended` flag makes cleanup idempotent. Late callbacks can touch only the
  context captured by their own operation and cannot annotate or end a newer
  run.
- A manual span ends exactly once on success, failure, cancellation, or
  synchronous setup failure. No session-lifetime span or finalizer guarantee
  is implied.
- A queued or rejected second launch cannot replace the active span handle.
- A late completion cannot end or annotate a newer run's span.
- Telemetry failures are caught at the internal adapter boundary even when
  `OTEL_ENV=dev`; they never replace the product result or original error.
- The adapter muffles synchronous R message and warning conditions raised by
  its provider calls. Direct stdout/stderr writes and asynchronous exporter
  diagnostics remain host-provider behavior and are outside Tempest's output
  guarantee.
- Tempest contains no exporter or network client and makes no explicit export
  call. A host-configured provider may perform its own export when spans end;
  Tempest does not configure, flush, or shut down that provider.

## Ownership

Keep the adapter isolated from product authority code:

| Owner | Responsibility |
|---|---|
| `R/otel.R` | gate, fixed names, allowlists, provider facade, safe attributes, span lifecycle |
| `R/progress-events.R` | observe newly emitted live events without changing callback semantics |
| `R/storm*.R` | STORM run boundary and async worker opt-in handoff |
| `R/stage-record.R` | synchronous and asynchronous stage executor boundaries |
| `R/costorm*.R` | Co-STORM completion, turn commit, warmup, report, and async cancellation boundaries |
| retriever owner | search/fetch spans and safe cache/count attributes |
| `inst/shiny/R/mod_storm.R` | pass only the validated boolean opt-in to its worker |
| host docs | opt-in configuration and external Collector examples |

Do not put provider configuration in `TempestConfig`, persistence, the Shiny
store, or the trajectory review. Do not add a generic observer framework.
